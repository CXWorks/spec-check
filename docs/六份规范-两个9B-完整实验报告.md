## 一、实验想回答什么

**核心问题：我们微调出来的 9B，在没见过的规范文档上，比原始的 9B 更强还是更弱？**

之前所有评测都在 **RMM** 这一份文档上做。微调模型在那里表现很好（留出集 49 条上正确 15–17 条，远超通用模型）。但那是**域内**——训练数据就来自同一份规范的其他版本。

**换一份完全不同的规范文档会怎样？** 这个问题之前提过两次，一直没做。这次做了，而且一次做了六份。

## 四、从 PDF 到可评测数据：两个抽取器

一份 PDF 不能直接喂给模型，要先切开。这一步做了两个工具。

### 抽取器一：PDF → 每条命令一个文件

```
DEN0056F_SCMI.pdf (224 页)
      ↓  pdftotext -layout
一整份纯文本
      ↓  找命令标题 → 切到下一条命令 / 下一个同级标题
training-dataset/sections/scmi/
    3.2.2.1_PROTOCOL_VERSION_command.txt
    3.2.2.3_PROTOCOL_ATTRIBUTES_command.txt
    ... × 153
```

切出来的每个文件就是**喂给模型的输入**——模型一次只看一条命令的说明。

脚本：`training/extract_sections_generic.py`。六份文档各有一套配置，因为标题格式完全不同：

| 文档 | 命令标题的样子 | 特殊处理 |
|---|---|---|
| PSCI | `5.6  CPU_ON` | 一个标题可含两条命令（`A and B`、`A/B`）|
| SDEI | `5.1.2  SDEI_EVENT_REGISTER` | —— |
| DRTM | `3.2  DRTM_VERSION` | —— |
| FFA | `13.2 FFA_VERSION` | 页脚 `13.14. FFA_ABORT` 带尾点，需区分 |
| **SCMI** | `3.2.2.1  PROTOCOL_VERSION` | **命令名跨协议重复**，用小节号限定 |
| **SBI** | `4.1. Function: Get SBI spec version (FID #0)` | **标题是人话**，真名在下一行的 C 声明里 |

**带自检**：`--selftest` 用这套代码重建 PSCI，和已有的 22 条逐条比对，**必须完全一致**才认。

### 抽取器二：每条命令声明了哪些返回码

rule check 要有一个「文档声明了什么」的清单，才能问「模型写到了吗」。

**这里和 RMM 有个本质差别**：

> RMM 的命令声明**具名输出**（`out_top`、`rtt_tree`），所以「这个输出被约束了吗」是直接问题。
>
> 这六份是 **SMC 调用约定**的 API——结果是一个寄存器里的值，用**错误码**描述，**没有具名输出清单**。

所以能迁移的是**返回码**那一问。脚本：`scripts/extract_returns.py`。

**词汇表取自文档自己的码表**，不是猜的：

| 文档 | 码表位置 | 码数 | 有独立 Return 段的命令 |
|---|---|---|---|
| PSCI | Table 5 Return error codes | 10 | 2/22 (**9%**) |
| SDEI | 5.3 Return codes / Table 6 | 6 | 19/19 (100%) |
| DRTM | 3.18 Return codes / Table 20 | 12 | 9/11 (81%) |
| FFA | Table 12.2 Error status codes | 10 | 5/39 (**13%**) |
| SCMI | Table 5 Status codes | 13 | 138/153 (90%) |
| SBI | Table 1 Standard SBI Errors | 15 | 72/72 (100%) |

**覆盖率差距极大（9%–100%），所以后面所有结果按文档分开报，不做平均。** 没有独立 Return 段的命令走全节扫描，结论更弱。


### 抽取器一是怎么写的

一份 PDF 切不好，后果不是报错，而是**安静地给出一批看起来很正常的错数据**。所以这个脚本的重点不在切，在**边界**和**验证**。

**第一步：PDF → 纯文本**

```bash
pdftotext -layout <文档>.pdf -
```

`-layout` 保留列对齐，表格才读得出来。

**第二步：去掉每页重复的噪音**

页眉页脚、版权行、目录的点线、孤零零的页码，逐行滤掉。共用一套，每份文档再加自己的：

```python
COMMON_NOISE = [
    r'Copyright.*(?:ARM|Arm|Limited)',
    r'^Non-Confidential',
    r'^Page\s+\d+\s+of\s+\d+',
    r'\.{4,}\s*\d+\s*$',          # 目录的点线
    r'^\d+\s*$',                  # 孤立页码
    r'^Chapter \d+\.',            # running header
]
```

**第三步：找命令标题**

每份文档一条正则。关键技巧是**要求名字位于行尾**（`\s*$`）——目录里的同名条目后面跟着点线和页码，这样就自动排除了，不需要额外判断目录范围。

```python
"sdei": r'(?m)^\s*(\d+\.\d+(?:\.\d+)?)\s+(SDEI_[A-Za-z0-9_/ ]*[A-Z0-9_])\s*$',
```

**第四步：定边界——这里最容易出错**

一条命令的文本从它的标题开始，到哪里结束？三个约束同时用：

```python
hard = 下一条命令标题的位置
depth = 本命令小节号的层级          # "3.13" 是 2 层，"5.1.2" 是 3 层
for h in 后面所有的编号标题:
    if h 的层级 <= depth:           # 同级或更高 → 是边界
        hard = min(hard, h 的位置)
        break
```

**为什么不能只用「下一条命令」**：某章的**最后一条**命令后面没有下一条了，于是它会一路吞掉后面的类型定义、附录、甚至整份文档剩余部分。这个坑在三份文档上各踩过一次（`DRTM_PARAMETERS` 1704 行、`FFA_MSG_POLL` 1637 行、RMM 2.0 的 `PSCI_VERSION` 3554 行，而正常中位数是 30–70 行）。

**为什么要比「层级」而不是「任意标题」**：命令自己的子小节（`5.6.1 Intended use`）比命令深一层，**不能**当边界；而下一个同级小节（`3.14 ...`）**必须**当边界。

**第五步：定名字**

三种情况：

| 情况 | 例子 | 做法 |
|---|---|---|
| 一个标题一条命令 | `5.6 CPU_ON` | 直接用 |
| 一个标题两条命令 | `5.9 MIGRATE_INFO_TYPE and MIGRATE_INFO_UP_CPU`<br>`5.22 PSCI_STAT_RESIDENCY/COUNT` | 按 ` and ` 和 `/` 拆开 |
| 标题是人话，真名在正文 | `4.1. Function: Get SBI spec version (FID #0)`<br>下一行是 `struct sbiret sbi_get_spec_version(void);` | 用 `name_from` 正则去正文取 |

拆开之后还要过一道**标识符过滤**：`" and "` 也会把散文标题拆开（`Arguments and return values in PSCI` → 两个假命令），所以只保留全大写标识符形状的。

SCMI 还有一层：**命令名跨协议重复**（每个协议都有自己的 `PROTOCOL_VERSION`），要用小节号限定。**注意限定要放在名字后面**（`POWERCAP_DOMAIN_NAME_GET__3_10_3_13`）——放前面会让生成的函数名以数字开头，不是合法标识符。

**第六步：自检（最重要的一步）**

```bash
python3 training/extract_sections_generic.py --selftest
```

用这套代码重建 **PSCI**，和已提交的 22 条逐条比对，**命令集合必须完全一致**。

这一步是唯一能提前发现静默错误的办法。写这个脚本时，自检在碰任何新文档之前就抓出了三个 bug：`18/22`（多命令标题被漏）、`20/22`（标题里的小写 `and`）、`24/22`（散文标题被误拆成假命令）。

另外脚本会在**最长小节超过中位数 10 倍**时告警——上面那几个跑过头的案例都是这么被发现的。

### 抽取器二是怎么写的

目标：**每条命令，文档声明了哪些返回码。**

**第一步：找文档自己的码表，不要用启发式**

每份规范都在某处用一张表定义全部返回码。这张表是权威来源：

| 文档 | 码表 |
|---|---|
| PSCI | `Table 5 Return error codes` |
| SDEI | `5.3 Return codes` / Table 6 |
| DRTM | `3.18 Return codes` / Table 20 |
| FFA | `Table 12.2: Error status codes` |
| SCMI | `Table 5: Status codes` |
| SBI | `Table 1. Standard SBI Errors` |

**定位时要取最后一个匹配**：同样的标题在目录里也出现一次，而且排在前面；取第一个匹配会读到目录，那里一个码都没有。

**第二步：从表里读码名，两种列序都要支持**

```
DRTM / SDEI / PSCI / SCMI          FFA
  SUCCESS        0                   -1    NOT_SUPPORTED
  NOT_SUPPORTED  -1                  -2    INVALID_PARAMETERS
  ↑ 名字在前                          ↑ 值在前
```

而且**缩进完全不可预测**——DRTM 顶格、SDEI 缩约 10 格、PSCI 约 38 格、FFA 约 60 格。所以不能限制缩进量，靠的是「**必须是行首第一个 token，且后面要有第二列**」。

**第三步：从每条命令的 Return 段里挑出现的码**

```python
m = re.search(RETURN_HEAD[doc], 命令文本)     # 找 "Return" 段
候选 = CODE.findall(该段前 3000 字符)
```

找不到 Return 段的命令，退化成扫描整节，并标记 `weak_source`——**这类命令的结论更弱，报的时候要能剔除**。

**第四步：两道过滤**

1. **命令名不是返回码。** 抽取器一的产物正好是命令名清单，直接拿来滤掉 `SDEI_EVENT_REGISTER`、`FFA_VERSION` 这类误判——免费。
2. **Arm 文档编号不是返回码。** `DEN0077A` 在页脚顶格出现、后面跟着版权行，形状和表格行一模一样。

**为什么不用「跨命令复现」这种启发式**：试过，它会把领域缩写提升成返回码——`ELC`、`IRQ`、`CRTM`、`DLME`、`PCR`、`TPM` 全被算成了码。**文档自己的表才是对的**。

**结果**：六份文档全部从各自的码表抽出，与原表精确一致，无缩写污染。

### 词汇表（preamble）

「尾部 200 行」和「按需选取」两种配置要给模型看一份词汇表。这六份文档没有现成的，用 `scripts/make_preamble.py` 生成：

- 共享的基础类型别名（`UInt64`、`Address` 等）
- **返回码常量**——来自抽取器二
- **功能 ID**——从各命令的参数表里刮（SDEI 有 13 个）
- 一个不透明的 state 结构

**这份词汇表只作为提示词上下文，不参与编译**，所以不需要是合法 Verus。rule check 全程不调用 Verus。

## 五、三种配置是什么

三种配置的差别只有一个：**给模型看多少词汇表**。

| 配置 | 给什么 |
|---|---|
| **不给字典**（nopre） | 只给这条命令的章节文本 |
| **尾部 200 行**（tail） | 章节文本 + 词汇表的最后 200 行 |
| **按需选取**（sel） | 章节文本 + 词汇表里这条命令用得上的部分 |

### 为什么不是五种配置

历史上还有两种「+ 改三轮」的配置（让模型看编译报错后自己改三次）。**这次没跑，有两个原因：**

1. **修复循环靠 Verus 编译驱动**，而 rule check 全程不编译，这两个配置在这里没有落点
2. **实测它不改变 rule check 结果**——在 RMM 上跑过全部五种配置，**修复配置和它对应的非修复配置的悬空输出结果一致**。原因很直接：**「输出没被约束」不是编译错误，修复循环看不见它**

## 六、怎么跑的

**硬件**：`research-common` 集群的一个节点，`jisenli-dev-0`，**8 × H100 80GB**。

**环境**：`nvcr.io/nvidia/pytorch:26.02-py3` + `transformers 5.15.0` + `peft 0.20.0`（与历史评测的 pin 一致，保证可比）。

**任务矩阵**：

```
6 份文档 × 2 个模型 × 3 种配置 = 36 组
316 条命令 × 6 组             = 1896 份生成规范
```

**调度**：一组占一张卡，8 组一批（**一张卡跑两个 9B 会 OOM**），跑完下一批。

**单组命令**（以 SCMI 的微调版 + 按需选取为例）：

```bash
python3 scripts/gen_specs.py \
  --base Qwen/Qwen3.5-9B \
  --adapter jisenli/spec-check-ckpt --subfolder sft3-2/final \
  --prompt-variant v3.1 --versions scmi --no-gold \
  --with-preamble --preamble-mode selected \
  --out-dir <输出目录>
```

原始模型就是**去掉 `--adapter` 和 `--subfolder` 两行**。

**完成判定按产出文件数**：每组生成的 `.rs` 文件数必须等于该文档的命令数，36 组全部精确相符。

## 七、测了什么指标

六份都没有 gold，所以**测不了正确率**。测的是这四项，**都不需要编译**：

| 指标 | 定义 | 意义 |
|---|---|---|
| **空洞 `true`** | 函数体字面就是 `true` | **最重要**。这种规范编译 100% 通过、允许一切行为，等于什么都没说 |
| **命中返回码** | 规范里提到了文档声明的返回码（至少一个） | 模型有没有真的读文档 |
| **复读** | 子句去重后少于原数的 60% | 未微调模型的典型退化 |
| **中位字符数** | 生成规范的长度中位数 | 辅助参考 |

**返回码匹配做了前缀容忍**：词汇表把码命名为 `<前缀>_<码>`，所以裸码、加前缀、加两次前缀三种写法都算命中。

## 九、结果分析

### 1. 微调模型在五份文档上大量输出空洞规范

`PSCI / SDEI / DRTM / FFA / SBI` 上，微调版的空洞率是原始模型的 **5–16 倍**，最高到 95%。

具体看一条（PSCI 的 `CPU_ON`）：

```rust
// 原始模型
pub open spec fn cpu_on_spec(result: int, old_s: S, new_s: S) -> bool {
    (result == PSCI_INVALID_PARAMETERS ==> (old_s.cpu_state[0] != 0))
    && (result == PSCI_ALREADY_ON      ==> (old_s.cpu_state[0] != 0))
    && (result == PSCI_SUCCESS         ==> (new_s.cpu_state[0] == 0))
}

// 微调版
pub open spec fn cpu_on_spec(entry_point: Address, context_id: ContextId,
                             result: int, old_s: S, new_s: S) -> bool {
  true
}
```

**这符合训练里一条已知的风险**：训练信号奖励「能编译」，而 `true` 是编译通过率最高的答案。域内有 gold 兜着看不出来，**换一份文档就暴露了**。

### 2. SCMI 一度看起来是反例，查清楚了：不是

初次统计时 SCMI 显示微调版只有 1–3 条空洞（153 条里），和其余五份完全相反。**单独查过之后确认是统计错误，不是真实现象。**

原因：SCMI 的命令名跨协议重复（每个协议都有自己的 `PROTOCOL_VERSION`），抽取器当时用小节号**前缀**去重名，于是生成的函数名长这样：

```rust
pub open spec fn 3.10.3.13_powercap_domain_name_get_spec(...) -> bool {
  true          // ← 函数体确实是 true
}
```

**以数字开头，不是合法标识符**，规范解析器认不出来，空洞检测静默回退成扫描全文——而全文当然不等于 `true`，于是判成「非空洞」。

**更正后 SCMI 与其余五份完全一致**：微调版 93/131/126（61%–86%），原始模型 13/24/18（8%–16%）。

抽取器已改成把小节号放在名字**后面**。另外核过全部六份的解析失败率：**PSCI / SDEI / SBI 为零**，DRTM 1 份、FFA 6–8 份，已一并更正。

### 3. 原始模型更会用文档自己的返回码

```
SCMI   base 32/117/126   vs   微调 2/6/8
FFA    base 10/23/33     vs   微调 2/1/3
PSCI   base  6/19/22     vs   微调 0/2/1
```

**给词汇表能大幅提升 base 的命中**（SCMI 从 32 涨到 126，FFA 从 10 涨到 33），**但对微调版几乎无效**——一个写 `true` 的规范不需要任何返回码。

**唯一例外还是相关的两份**：SBI 上微调版命中 26/17/13，不算低；SCMI 上微调版空洞率最低但命中也只有 2/6/8。

### 4. 原始模型的代价：退化

原始模型不是全面更好。它会**复读**（同一个子句重复到撞 6144 token 上限）：

```
SCMI  base 复读 18/13/14 条（153 条里）
SBI   base 按需选取时复读 11/72
```

微调版的复读几乎为 0。**所以准确的说法是：微调版稳定但空洞，原始模型有内容但控制不住。**

### 5. 「命中返回码」不等于「写对了」

这一列只说规范里**提到了**文档声明的码，**不说用得对不对**。判对错需要人工或 gold，**这六份都没有**。

---

## 十、限制

1. **没有 gold，测不了正确率。** 全部结论建立在空洞率、命中率、复读率上，这三项都不衡量语义正确性。
2. **返回码段覆盖率差距极大**（PSCI 9%、FFA 13% vs SBI/SDEI 100%）。前两份的码是全节扫描得到的，结论明显更弱。
3. **只跑了三种配置**，两种「改三轮」配置没跑（理由见第五节）。
4. **单次贪心解码**，没有多次采样，没有统计显著性检验。
5. **空洞率依赖规范解析。** 解析失败会让空洞被漏记（SCMI 就因此一度被误报），现在改用容忍解析，并会同时报解析失败数。
