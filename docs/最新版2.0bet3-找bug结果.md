# 在最新版规范（2.0 BET3）上找 bug

**老板问**：能不能在最新版的同一份文档上试试，看有没有新 bug。

**答案**：能，而且有。**我们在旧版找到的 bug 一个都没修，另外还发现了 5 条新命令有同样的毛病。**

---

## 两个版本

| | 我们之前用的 | 最新版 |
|---|---|---|
| 版本 | 1.1-alp14 | **2.0 BET3** |
| 发布 | —— | **2026-08-08** |
| 页数 | 643 | **847** |
| 命令数 | 98 | **121** |

文档从 ARM 官方接口取的（`isConfidential: false`，公开文档），已存进 `specs/`。

---

## 一、旧 bug：一个都没修

### `RMI_RTT_SET_S2AP` —— 原封不动

输出表里还是声明着 `rtt_tree`，成功条件表里还是只定义了 `out_top`：

```
【输出值】  result / out_top / rtt_tree
【成功条件】 ID          Condition
            s2ap_addr   post: rec.s2ap_addr == out_top      ← 只有这一条
                                                            ← rtt_tree 从不出现
```

**和 alp14 逐字相同。这个洞原样留到了最新版。**

### `RMI_PSMMU_IRQ_NOTIFY` —— 改了结构，但洞还在

这条命令**被重新设计过**了：

```
alp14 :  6 个输出   result, action, rd, vsmmu, msi_addr, msi_data
bet3  :  2 个输出   result, flags        ← 那 5 个被合并成一个 flags
```

看起来像修好了。**但成功条件表还是那句话**：

> The RMI_PSMMU_IRQ_NOTIFY command does not have any success conditions.

**`flags` 这个输出，照样没有任何条件定义它的值。**

**是重构，不是修复**——洞变小了（5 个输出变 1 个），但性质没变。

---

## 二、新 bug：5 条新命令，同样的毛病

这 5 条在 alp14 里**根本不存在**，是 2.0 新增的（主要是虚拟 SMMU 和设备相关）：

| 命令 | 没定义的输出 | 成功条件表 |
|---|---|---|
| `RMI_VSMMU_CMD_COMPLETE` | `flags` `vsid` `msi_addr` `msi_data` | **原文写着"没有任何成功条件"** |
| `RMI_VSMMU_CMD_GET` | `flags` `vsid` `msi_addr` `msi_data` | **原文写着"没有任何成功条件"** |
| `RMI_VSMMU_EVENT_HANDLE` | `fipa` `syndrome` | 表不空，但这两个从不出现 |
| `RMI_RTT_DEV_UNMAP` | `out_count` | 表不空，但它从不出现 |
| `RMI_RTT_UNPROT_UNMAP` | `out_count` | 表不空（`out_top`、`out_range` 都定义了，**唯独漏了 `out_count`**）|

**前两条最严重**：和老的 `RMI_PSMMU_IRQ_NOTIFY` 一模一样的形态——声明了 4 个输出，然后一句"本命令没有任何成功条件"，**4 个值全部悬空**。

**最后一条最像笔误**：`RMI_RTT_UNPROT_UNMAP` 有三个输出 `out_top` / `out_range` / `out_count`，前两个都老老实实定义了，**第三个被漏掉了**。这种一眼能看出是遗漏而不是设计。

## 三、汇总

| | alp14 | 2.0 BET3 |
|---|---|---|
| 有悬空输出的命令 | 3 | **7** |
| 其中"成功条件表明确为空" | 1 | **3** |
| 命令总数 | 98 | 121 |

**新增的 23 条命令里，有 5 条带着这个毛病进来的。** 问题不是在收敛，是在**跟着新功能一起增长**。

---

## 四、这些数字是下限，不是全部

**必须说清楚**：这次是直接解析 PDF，而 PDF 表格提取会失败。

- **17 条命令的输出表被 `pdftotext` 打散成竖排**，解析不出来，**没有被检查**（alp14 上是 18 条）。真实数字只会更多，不会更少。
- 工具还会**多报**。它一度说 `RMI_PSMMU_IRQ_NOTIFY` 有 6 个悬空输出，我翻原页发现实际只有 `flags` 一个。
- **所以上面每一条我都人工翻了原文确认**，表里列的是确认过的，不是工具的原始输出。

工具的定位是**筛出候选**，不是给结论。两份文档用的是同一把尺子、同样的盲区，**所以"新增了 5 条"这个比较是成立的**，即使绝对数不全。

## 五、和之前工作的关系

之前在 alp14 上找 bug，用的是**三方对照**（文档 + 人类专家写的标准答案 + 我们的 9B 模型），可信度更高——如果连专家也留空，基本能确定是文档的问题。

**这次没有那两方**：2.0 BET3 没有人写过标准答案，我们的模型也没在上面跑过。所以这次是**纯文档检查**，只问一个问题：输出表里声明了，条件表里提到了吗？

**好处是快**——拿到 PDF 到出结果不到一小时，不需要 GPU。

**代价是**：分不清"文档真没写"和"文档写在别处了"。像 `RMI_RTT_READ_ENTRY` 的 `desc` 那种——条件表里没有，但正文有一句话加一个跨文档引用——这种就需要人判断。（`desc` 在 2.0 BET3 里**依然是这个状态**。）

### 模型对照已经补上了（2026-09-15）

9B 在 2.0 BET3 的 121 条上跑过了（两个配置），**结论是模型独立复现了几乎全部发现**——
上面每一条文档缺陷，模型读了同一份文档也把同样的输出留空了。

**所以现在是两方一致，不再是工具单方面说了算。**

两处例外值得记：

- `RMI_VSMMU_CMD_GET`：`sel` 配置**根本没在签名里声明那 4 个输出**，属于生成时丢参数，不算佐证
- `RMI_RTT_DEV_UNMAP` / `out_count`：`tail` 给了约束、`sel` 留空，**两个配置判断相反**，这条不如 `RMI_VSMMU_CMD_*` 硬

反过来 `RMI_RTT_READ_ENTRY` / `desc` **更确定了**：alp14 上两个配置意见相左，2.0 上两个都留空。

明细见 [进展与计划](2.0bet3-进展与计划.md)。

**编译率不在这里报**：2.0 把 `RmiCommandReturnCode` 改名成 `RmiResult`（出现 104 次），
186 种类型里 71 种旧词汇表没有，编译率掉到 8%。**那是拿旧字典考新课本，不是模型成绩。**

## 怎么复现

```bash
python3 scripts/spec_gap_scan.py --pdf specs/DEN0137_2.0-bet3_rmm-arch_external.pdf
python3 scripts/spec_gap_scan.py --pdf specs/DEN0137_1.1-alp14_rmm-arch_external.pdf
```

```bash
curl -sL https://documentation-service.arm.com/documentation/den0137/latest \
  | python3 -c "import json,sys;print(json.load(sys.stdin)['_links']['resources'][0]['href'])"
```

原始结果：`results/specgap/`。
