## 2. 结论速览

### 文档拿到了

ARM 官网那个页面是 JS 应用，HTML 里没有 PDF 链接，翻接口才拿到：

```
documentation-service.arm.com/documentation/den0137/latest
  → DEN0137_2.0-bet3_rmm-arch_external.pdf
    847 页 · 121 条命令 · 发布 2026-08-08 · isConfidential: false（公开）
```

对比我们之前用的 alp14：643 页 · 98 条命令。**新增 23 条命令。**

### 旧 bug：一个都没修

| 命令 | 状态 |
|---|---|
| `RMI_RTT_SET_S2AP` / `rtt_tree` | **逐字未动**。输出表还声明着它，成功条件表还是只定义 `out_top` |
| `RMI_PSMMU_IRQ_NOTIFY` | **重构了，但洞还在**。5 个输出合并成 1 个 `flags`，成功条件表还是那句"本命令没有任何成功条件" |

第二条值得强调：**看起来像修好了（输出从 6 个变 2 个），其实没有。** 是重构不是修复。

### 新 bug：5 条新命令，同样的毛病

这 5 条在 alp14 里**根本不存在**，是 2.0 新增的：

| 命令 | 悬空输出 | 备注 |
|---|---|---|
| `RMI_VSMMU_CMD_COMPLETE` | flags, vsid, msi_addr, msi_data | **原文"没有任何成功条件"** |
| `RMI_VSMMU_CMD_GET` | flags, vsid, msi_addr, msi_data | **原文"没有任何成功条件"** |
| `RMI_VSMMU_EVENT_HANDLE` | fipa, syndrome | |
| `RMI_RTT_DEV_UNMAP` | out_count | |
| `RMI_RTT_UNPROT_UNMAP` | out_count | **像笔误**：`out_top`、`out_range` 都定义了，唯独漏了它 |

**有问题的命令数：alp14 是 3 条 → 2.0 是 7 条。问题没有收敛，是跟着新功能一起长。**

### 两点限制

- **这些是下限。** `pdftotext` 把 **17 条命令的输出表打散成竖排**，那些压根没被检查。
- **工具会多报。** 它一度说 `RMI_PSMMU_IRQ_NOTIFY` 有 6 个悬空输出，翻原页发现**实际只有 1 个**。表里每一条都人工核过原文。

**"新增 5 条"这个比较是成立的**——同一把尺子、同样的盲区，量了两份文档。

## 3. 第一轮为什么不够，第二轮要补什么

alp14 那次用的是**三方对照**：

```
文档原文  +  人类专家写的标准答案  +  我们的 9B 模型
```

三方都留空 → 基本可以确定是**文档的问题**，不是读的人不行。

**2.0 BET3 这次只有一方**：没人写过标准答案，模型也没跑过。所以只能问一个问题——"输出表声明了，条件表提到了吗"。

**分不清两种情况**：

| | 例子 |
|---|---|
| 文档真的没写 | `RMI_VSMMU_CMD_GET`：原文直说"没有任何成功条件" |
| 文档写在别处了 | `RMI_RTT_READ_ENTRY` 的 `desc`：条件表里没有，但正文有一句话 + 一个跨文档引用 |

第一种没什么可争的，第二种需要判断。

## 4. 第二轮：9B 模型对照（已完成）

在 2.0 BET3 的 121 条命令上跑了 9B，两个配置（`sel` 按需选取词汇表、`tail` 尾部 200 行），
`research-secure-05` 的 GPU 1 和 2，各约 1 小时。

**修复轮数的配置故意没跑**——修复要靠 Verus 编译，而词汇表缺 38%，每轮都会栽在找不到符号上，
量的是词汇漂移不是模型。

### 结论：模型独立复现了几乎全部发现

对第一轮确认的每一条，问一个问题——**模型读了同一份文档，是不是也把这个输出留空了**：

| 命令 | 文档没定义的输出 | sel | tail |
|---|---|---|---|
| `RMI_PSMMU_IRQ_NOTIFY` | `flags` | ✅ 留空 | ✅ 留空 |
| `RMI_RTT_SET_S2AP` | `rtt_tree` | ✅ | ✅ |
| `RMI_RTT_READ_ENTRY` | `desc` | ✅ | ✅ |
| `RMI_VSMMU_CMD_COMPLETE` | flags, vsid, msi_addr, msi_data | ✅ 4/4 | ✅ 4/4 |
| `RMI_VSMMU_CMD_GET` | flags, vsid, msi_addr, msi_data | ⚠️ 见下 | ✅ 4/4 |
| `RMI_VSMMU_EVENT_HANDLE` | fipa, syndrome | ✅ 2/2 | ✅ 2/2 |
| `RMI_RTT_DEV_UNMAP` | `out_count` | ✅ | ❌ 它给了约束 |
| `RMI_RTT_UNPROT_UNMAP` | `out_count` | ✅ | ✅ |

**从"工具说文档没定义"升级成了"另一个独立读者也认为文档没定义"。**

### 两处不一致，都值得记

**`RMI_VSMMU_CMD_GET`**：`sel` **压根没在签名里声明这 4 个输出**。这不是"也留空了"，
是另一种毛病——生成时把参数整个丢了。不能算作佐证。

**`RMI_RTT_DEV_UNMAP` / `out_count`**：`tail` **给它写了约束**，`sel` 留空。
两个配置读同一份文档得出相反判断，说明这条不像 `RMI_VSMMU_CMD_*` 那样板上钉钉。

**`RMI_RTT_READ_ENTRY` / `desc` 反而更确定了**：在 alp14 上两个配置意见相左（tail 留空、sel 没留），
**在 2.0 BET3 上两个都留空**。

### 模型还干了一件有意思的事

`RMI_PSMMU_IRQ_NOTIFY` 在 2.0 里只声明 2 个输出（`result`、`flags`），
但模型在签名里**多写了 5 个**：`event_num`、`sid`、`fetch_addr`、`input_addr`、`syndrome`。

这几个看着像是从 `RmiPsmmuIrqResult` 这个类型的字段里搬过来的。**属于模型自己加戏**，
和文档缺陷无关，但说明它会把类型定义里的字段误当成命令的输出。

### 编译率：词汇漂移的代价被量化了

| | alp14 | 2.0 BET3 |
|---|---|---|
| `sel` 能编译 | 69/98 (70%) | **10/121 (8%)** |
| `tail` 能编译 | 67/98 (68%) | **11/121 (9%)** |

失败原因里 `missing_symbol` 占大头（48 / 43 条）——**就是词汇表对不上**。

**这个 8% 不是模型成绩，不要这么读。** 2.0 把 `RmiCommandReturnCode` 改名成 `RmiResult`
（出现 104 次），186 种类型里有 71 种旧词汇表没有。**我们是拿旧字典去考新课本。**

**Z3 矛盾 / 空洞检查同理没有跑**——它也要先编译，在这个词汇表下没有意义。

### 要把编译那一路也做出来，需要什么

给 2.0 BET3 写一份自己的词汇表（preamble）。文档里有 `B4.6 RMI types` 这些小节，
类型定义是齐的，是可以做的，但**是一件独立的工程活**，不是跑一次模型的事。

**不做也不影响本文档的结论**——悬空输出检查从不调用 Verus。
