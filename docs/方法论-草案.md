# 方法论草案：一套能对任意规范 PDF 跑的「找 bug」流水线

> **这份文档是草案，不是结论。**
> 起因是一个想法：论文的卖点也许不该是「我们微调了一个模型」，而是
> **「我们有一套从 PDF 到人工确认 bug 的完整流水线」**。
> 想法本身还没想清楚，这里先把它写下来，把**已经有证据的部分**和
> **还只是设想的部分**分开标清楚，方便讨论时直接改。
>
> 每一节末尾的「**待定**」是需要拍板的地方。

---

## 0. 先说一个必须先想清楚的问题

流水线的目标是**在规范文档里找 bug**。但我们的机器筛查，查的是**模型生成的 Verus 规范**。
这两件事之间有一个假设：

> **只有当模型忠实地把文档翻译成规范时，「生成的规范自相矛盾」才等于「文档自相矛盾」。**

如果模型只是写了垃圾，那么筛查出来的问题是模型的问题，**跟文档一点关系都没有**。

这不是理论担忧。在 PSCI 上，我们的 9B **73% 的命令直接写了 `true`**（见
[工作说明第九部分](工作说明-中文.md)）。对这些命令，筛查结果对文档**零信息量**。

所以整条流水线的可信度，卡在一个我们**目前没有解决的**问题上：

> **在没有标准答案的新文档上，怎么知道生成的规范是不是忠于原文？**

这是全文最重要的一个洞，第 3 节和第 6 节会回到它。**我认为这应该是论文的核心贡献点，
而不是被当成 limitation 一笔带过。**

---

## 1. 流水线全貌

```
  规范 PDF
     │
 S1  ├─ 结构化切分：抽出每条命令的文本 + 把跨节引用解析进来
     │
 S2  ├─ 生成：每条命令 → 一个 Verus spec fn
     │
 S3  ├─ 机器筛查：不需要标准答案就能判的几类问题
     │
 S4  ├─ 人工确认：把候选缩到人能看完的量，人来判是不是真 bug
     │
 S5  └─ 上报：给规范维护方（ARM 等）提 erratum
```

**卖点应该是 S1+S3+S4 这一段，不是 S2。** S2（模型）是可替换的零件——
我们已经量到 Claude 在新文档上比我们的微调模型好（见第 2 节表），
**这恰恰说明流水线的价值不在那个模型上**。

## 2. S1 — 从 PDF 到「每条命令的完整上下文」

### 现在有什么

- 六个 RMM 版本 + PSCI 的抽取器（`training/extract_sections_*.py`）
- PSCI 上做了三档上下文，可以直接对比：

| 档位 | 每条命令平均行数 | 内容 |
|---|---|---|
| `psci_13` | 55 | 只有命令自己那一节 |
| `psci_13_full` | 91 | + 该命令的参数表（5.1.x） |
| `psci_13_closure` | 636 | + 传递闭包：把「见第 N 节」一路解析到不动点 |

### 量到了什么

**开会时提的「切分会不会拿不到完整上下文」，在不同文档上结论相反：**

- **RMM：98 条命令，0 条跨节引用。** 担心不成立。
- **PSCI：22 条命令，22 条都有，共 52 处。**

原因是排版结构，不是切分方式：**PSCI 把参数表和 Function ID 放在单独一章（5.1.x），
文字描述放在另一章（5.3–5.22）**；RMM 每条命令自己那节就带着表格。

**一个反直觉的发现：把参数表拼回去，未解析引用不降反升，52 → 72。**
因为参数表本身也含「见第 5.6 节」。**这不是一步能修好的事，是个传递闭包问题。**

**好消息是闭包收敛得很快，而且不大：**

| | 平均行数 | 占全文比例 |
|---|---|---|
| 只有描述 | 55 | 1% |
| 闭包 | 636 | 15% |
| 最大的一条（CPU_DEFAULT_SUSPEND） | 1813 | 42% |

**闭包平均只有全文的 15%，最坏 42%，没有一条会拉进整份文档。**
所以「把上下文补完整」在工程上是**可做的**，不是无底洞。

### 缺什么 / 弱点

- 闭包只跟着 **「section N」这种显式引用**走。图、表的交叉引用、以及「如前所述」这类
  没有编号的指代，**完全抓不到**。
- 抽取器是**每份文档手写一个**。要说「能对任意 PDF 跑」，这是最站不住的一环。
- 我在 PSCI 上连续犯了两次同样的错：**最后一节没有下一个标题可以停，一路吃到文档结尾**
  （5.22 变成 1460 行，5.1.22 变成 2599 行）。这类错**不会报错，只会让输入变脏**。

### 待定

1. 论文是主张「通用抽取器」还是老实说「每份文档要写一个适配器，但适配器很薄」？
   **我倾向后者**，因为前者我们没有证据。
2. 闭包要不要作为默认？**正在跑一个实验测它到底有没有用**（见第 7 节）。

## 3. S2 — 生成

### 现在有什么

微调的 Qwen（4B / 9B）+ 通用模型（Claude Opus 5）都能跑同一套输入。

### 量到了什么（PSCI，22 条命令，都无标准答案）

| 配置 | 能编译 | 空洞 | **真说了点什么** |
|---|---|---|---|
| 9B 只给章节 | 16/22 | 16 | **0** |
| 9B + 参数表 | 17/22 | 14 | **3** |
| Claude 只给章节 | 22/22 | 13 | **9** |
| Claude + 参数表 | 21/22 | 11 | **10** |

**读法很重要，不能直接读这四行：**

**8 条命令两个模型都判空洞**，这 8 条看起来是**文档本身就没约束**，不是模型的锅——
`SYSTEM_RESET` 全节 9 行、没有任何返回码；`PSCI_STAT_*` 原文明说「不支持错误码」；
`PSCI_VERSION` 返回一个版本号、不会失败。**对这些命令，写 `true` 可能就是对的。**

而且**只给章节时，Claude 判空洞的集合是 9B 的真子集**。

**所以有意义的比较是剩下 14 条**（文档确实规定了行为的）：
**Claude 写出真规范 10 条，我们的 9B 只有 3 条。**

### 这一节推翻了什么

**在 RMM 上（域内），我们的 9B 正确率 15/49，Claude 是 1/49，我们大幅领先。
在 PSCI 上（域外），两个能测的指标我们都输。**

**微调买到的优势是「域内」的，不迁移。**

这对论文其实是好事，只要**把卖点放在流水线而不是模型上**——S2 是可插拔的，
谁强用谁。但如果论文的主张是「我们的微调模型是核心贡献」，**这个结果是硬伤。**

### 待定

3. 论文主线是「流水线 + 可插拔生成器」，还是「微调模型」？**这两个走向不能兼得，
   现在的数据支持前者。**

## 4. S3 — 机器筛查（无标准答案也能判的）

### 现在有什么

`scripts/psci_sweep.py`，两个判据，都由 Z3 判定，**都不看标准答案**：

- **不可满足**：`requires SPEC ensures false` 能证 → 没有任何输入满足它，它把一切都禁止了
- **空洞**：`ensures SPEC` 能证 → 任何输入都满足它，它什么都没禁止

另外还有几个已有的、不需要答案的检查：悬空输出（声明了但没约束的输出）、
`scripts/provenance.py` 的文档溯源。

### 这一节最重要的一条经验

**一个「什么都没找到」的筛查器，和一个「坏掉的」筛查器，从输出上分不出来。**

仓库里已经有一个同类扫描器被记录为「近乎失明」（`OPUS5_RESULTS.md`，98 条报 0）。
所以新筛查器**自带 `--self-test`**：用重建的 bug 样例 + 诚实的反例跑一遍，打印混淆矩阵。
**所有报出来的数，旁边都必须附上这个自检结果**（本轮全部 6/6）。

**我认为这一条应该写进论文的方法论**：任何无监督筛查，都必须报告自己的检出能力，
否则数字没有意义。

### 我在这一步犯的错，值得写进论文的「威胁」一节

8 个并发的 Verus 进程往同一个文件名写产物，互相踩坏，报出来是 `LLVM error`。
**我的分类器把它归成「这条规范编译不过」——22 条里冤枉了 4 条。**

修好之后那 4 条全是空洞的，**所以这个修正让结果更差，不是更好**。

教训是：**「工具坏了」和「被测对象坏了」必须是两个不同的判定结果，不能合并。**

### 缺什么

- **目前只查了「模型输出的规范」有没有毛病，没有查「文档」有没有毛病。**
  这两者的桥梁就是第 0 节那个假设。
- 4 月那份 4B 的 PSCI 报告记了 3 个「不可满足」，**这次三个配置跑下来，一条都没有**。
  失败模式整个变了（从「写得复杂但矛盾」变成「直接写 `true`」）。
  但那 4 个 bug **无法复现**——当时的输出文件不在任何分支上。

### 待定

4. 要不要加「跨版本差分」作为第三个判据？RMM 有六个版本，
   **同一条命令在两个版本间语义变了但文档没说改**，这是很强的 bug 信号，
   而且**同样不需要标准答案**。我认为这是目前最值得加的一个判据。
5. 要不要把「空洞」拆成两类：**文档本身没约束**（对的）vs **模型没读懂**（错的）？
   现在混在一起，PSCI 那 8 条共同空洞就是证据。**不拆开，空洞数就不是一个能报的指标。**

## 5. S4 — 人工确认

### 现在有什么

RMM 上做过一轮：SCOPE 的 verus_rmm 基准，eac5 4 TP + 6 FP、rel0 3 TP + 6 FP，
**这些是人写的标准答案**，我们逐条手工核对过「找出来的原因和 SCOPE 写的是不是同一个」。

### 缺什么 —— 这是整条流水线最空的一环

**我们从来没有量过人工确认这一步的成本。** 没有：

- 每条候选平均要看多久
- 确认一个真 bug 平均要看几条候选（**精确率**）
- 不同的人判断一致吗（**标注者一致性**）

**没有这些数，「这套流水线能帮人找 bug」就只是一句口号。**

### 提议的核心指标

> **每个「已确认的文档 bug」花掉的人工分钟数。**

这个指标好在：它把 S1–S3 所有的改进都折算成同一个单位。筛查器精确率翻倍，
这个数就减半；模型更忠实，这个数也减半。**而且审稿人一看就懂。**

### 待定

6. 谁来做人工确认？需要懂 ARM 规范的人，**这是真实的成本，要提前排**。
7. 至少要两个人独立标一部分，才能报一致性。**样本量多少？**
8. 要不要设一个「诱饵」集（人为注入的已知 bug）来估召回率？**没有它我们永远只能报
   精确率，报不了召回率。**

## 6. 回到第 0 节：怎么衡量「忠于原文」

这是我认为**最值得做成论文贡献**的一块，目前只有半成品。

### 已有

`scripts/provenance.py`：把生成的每个子句和文档的行做对应，看覆盖率和归属。
`scripts/clause_equiv.py`：把分歧定位到具体的文档行。

**这两个工具的局限我都实测过并记录了**：provenance 的「凭空捏造子句」指标
拿已知的 `walk_level` 幻觉去测，**它没抓到**，所以那个指标被撤回了。

### 设想（**未实现**）

让模型在生成每个子句时，**同时输出它依据的文档行号**。然后：

- 行号对不上 → 直接判「无依据」
- 文档某行没有任何子句引用 → 「漏了」
- 两者都能**自动算，不需要标准答案**

这是我目前想到的**唯一一个能在无标准答案文档上自动测忠实度**的办法。

### 待定

9. 这个要不要做？**需要改 prompt 重新生成一遍**，成本不低，但如果论文要主张
   「可以用在任意新文档上」，**没有忠实度指标这个主张就是空的**。

## 8. 这套东西目前最站不住的三点（先自己说，别等审稿人说）

1. **「文档 bug」和「模型 bug」还没分开。** 筛查查的是模型输出；只有模型忠实时，
   结论才落到文档上。而忠实度我们**测不了**。
2. **抽取器是每份文档手写的。** 说「能跑任意 PDF」证据不足。
3. **人工那一步完全没量化。** 没有精确率、没有一致性、没有召回率。

**我认为 1 和 3 是必须补的，2 可以老实承认并缩小主张范围。**
