# 在 alp14 规范里找 bug：找到了什么，怎么找的

> 面向没接触过这套工具链的人。先讲清楚「bug」在这里到底指什么，再看结果。

---

## 一句话

我们在 ARM 的 alp14 规范（643 页）里找到了 **2 处真正的文档漏洞**——**规范说某个命令会返回某个值，却从头到尾没说这个值应该等于什么。**

---

## 第一部分：这里说的「bug」是什么

### 不是程序崩溃，是文档没写清楚

ARM 的这份规范是给芯片厂商看的说明书。它规定「RMM」这个安全模块的每条命令：给它什么输入、它返回什么输出、什么情况下报错。

**一条命令的说明书长这样：**

```
命令：RMI_PSMMU_IRQ_NOTIFY

【输出值】表格里列着，这条命令会返回 6 个东西：
    result      —— 成功还是失败
    action      —— 需要 Host 做什么动作
    rd          —— 某个地址
    vsmmu       —— 某个地址
    msi_addr    —— 某个地址
    msi_data    —— 某段数据

【失败条件】表格：什么情况下返回错误码 ...（这张表写得很详细）

【成功条件】表格：成功时这些输出各自等于什么？
```

**问题就出在最后这张表。它的全文只有一句话：**

> The RMI_PSMMU_IRQ_NOTIFY command does not have any success conditions.
> （本命令没有任何成功条件。）

**表是空的。**

### 为什么这是个 bug

说明书告诉你「这条命令会返回 `msi_addr` 这个地址」，但**从来没说这个地址应该是多少**。

拿这份说明书去实现芯片的两个厂商，一个可能返回 0，一个可能返回别的东西，**两边都不算违反规范**——因为规范压根没规定。而这是个**安全模块**，Realm 的机密性靠它保证。

这就是我们要找的东西：**声明了输出，却从不定义它的值。**

---

## 第二部分：怎么判断的

难点在于——**模型没写这个输出，到底是文档没写，还是模型自己漏了？** 这两件事看起来一模一样，但意义完全相反。

所以我们让**三方同时上场**：

| 角色 | 是什么 |
|---|---|
| **规范原文** | ARM 的 PDF，`成功条件` 表里到底有没有提到这个输出 |
| **标准答案（gold）** | **人类专家**读同一份 PDF 写出来的数学化规范 |
| **我们的 9B 模型** | 5 种不同配置各写一遍 |

然后看**谁留空了**：

```
文档里有定义  +  模型留空        →  模型的锅（漏读了）
文档里没定义  +  模型留空        →  ✅ 文档的锅 ← 这就是 bug
文档里没定义  +  模型硬写了一个   →  模型在瞎编
```

**人类专家（gold）是关键的对照组。** 如果连专家读了 PDF 也留空，那基本可以确定**不是读的人不行，是文档真没写**。

---

## 第三部分：找到了什么

### ✅ 2 处文档漏洞（专家和模型全部一致留空）

| 命令 | 没定义的输出 | 人类专家 | 我们的 5 个配置 |
|---|---|---|---|
| `RMI_PSMMU_IRQ_NOTIFY` | `action` `rd` `vsmmu` `msi_addr` `msi_data`（5 个）| 留空 | **全部留空** |
| `RMI_RTT_SET_S2AP` | `rtt_tree`（1 个）| 留空 | **全部留空** |

**第一条**就是上面讲的例子：成功条件表原文写着「没有任何成功条件」。

**第二条更微妙**：`rtt_tree` 这个输出**只在正文里被一句话提了一下**——

> *rtt_tree* is the index of the RTT in which the base alignment check failed.
> （rtt_tree 是基址对齐检查失败时所在的 RTT 的编号。）

这是**一句散落的说明文字，不是结构化的条件表**。而真正的成功条件表里，只定义了 `out_top` 一个输出，`rtt_tree` 从头到尾没出现。

**为什么"只有一句话"不够**：结构化的表是可以被机器翻译成数学式子的（`post: rec.s2ap_addr == out_top`），散句不行。真正实现芯片的人照着表写代码，很容易就漏掉散落在别处的那一句。

### 有多可信

**这两条，当年用 4B 小模型做的那次分析也是同样这两条**（`OUR_CODE_RULE_CHECK.md`）。

这次是**换了大模型（9B）、换了完全不同的数据抽取方式**，**独立跑出了一样的结果**。两次互相印证。

### 顺便回答「是 2 个还是 4 个」

之前有说法是那次分析找到「4 个真实文档缺陷」。**我查了原文，是 2 个。**

- 那份文档里两处写到数字，**都是 2**
- 当时另外还标记了 9 条，但被**明确判定为「模型自己漏了」，不是文档的问题**
- 这次独立重跑，还是 **2 条命令**

如果按**输出个数**数（5 + 1），是 **6 个**。**按命令数是 2，按输出数是 6——没有哪种数法得到 4。**

## 第四部分：另外三个发现

### 1. 规范里没有自相矛盾的地方（这是个干净的结论）

我们还做了第二种检查：**让定理证明器 Z3 去找「自相矛盾」的规范**——就是那种"要求 A 同时要求非 A"、任何实现都不可能满足的条款。

**98 条命令，一条都没有。连人类专家写的标准答案也没有。**

这个「零」是可信的，因为：

- 检查器每次运行前都跑**自检**：拿 6 个已知答案的样例喂给它，**6 个全部判对**才继续
- 标准答案也一起跑了——**如果是工具坏了，标准答案会一起挂**

（后面「过程中修的 bug」那节会讲到，工具确实坏过一次，就是靠标准答案全挂才发现的。）

### 2. 有 3 条命令，规范本身什么都没规定

`PSCI_CPU_OFF`、`PSCI_CPU_SUSPEND`、`PSCI_FEATURES` 这三条，**人类专家写的标准答案就是一句「永远成立」**——因为文档确实没给出任何约束。

**我们的 5 个配置，一条不差地复现了同样这 3 条。**

也就是说：**模型和人类专家，在"哪里文档没东西可写"这件事上判断完全一致。**

### 3. 人类专家自己也漏了 3 处

反过来也有：**文档明明定义了，标准答案却没写进去。**

| 命令 | 漏掉的输出 | 谁漏了 |
|---|---|---|
| `RSI_IPA_STATE_GET` | `ripas` | 专家 + 全部 5 个配置 |
| `RSI_IPA_STATE_GET` | `out_top` | **只有专家漏了** |
| `RSI_MEM_SET_PERM_INDEX` | `new_cookie` | 专家 + 4 个配置 |

**中间那条：模型写对了，人类专家漏了。**

### 附带：9B 比 4B 强很多

当年 4B 那次，11 条被标记里有 **9 条是模型自己漏读了文档**。

这次 9B，每个配置**只有 1–2 条**，而且大部分连专家也漏。

**模型从「读不全说明书」进步到了「和专家漏得差不多」。**

## 第五部分：有一条我不下结论

`RMI_RTT_READ_ENTRY` 这条命令的 `desc` 输出，**证据两可，需要人来拍板。**

情况是这样：

```
输出表里声明了：  desc,  64 位,  "RTTE 描述符"

成功条件表里：    约束的全是 rtte.attr_unprot、rtte.s2ap_*、rtte.addr
                 —— 是 rtte 这个结构的各个字段
                 —— 从来没有一句 "desc 等于什么"

唯一的绑定来自正文一句话：
   "desc 输出值里各字段的布局和编码，与《Arm 架构参考手册》中
    '阶段 2 VMSAv8-64 块和页描述符的属性字段' 一致。"
   —— 是散句，而且指向的是另外一份文档
```

**各方表现也不一致**：2 个配置留空了（认为文档没定义），**而人类专家和另外 3 个配置反而给它编了一个约束**。

**这一条到底算不算文档漏洞，取决于「指向另一份文档的交叉引用」算不算定义。这是个判断题，不是计算题，我不替人做。**

> 补充一点：eac5 那版规范里有个已知 bug 是 `walk_level` 没定义——**在 alp14 里已经修好了**（表里明确写了 `walk_level == walk.level`）。

## 第六部分：过程中修掉的 3 个 bug（都影响结论）

这次的结果不是一次跑出来的。中间工具坏过，而且**坏的方式很像"真结果"**：

| 出了什么问题 | 如果没发现会怎样 |
|---|---|
| 检查工具假设规范词汇表以某个固定格式结尾，alp14 不是，导致**文件被从中间截断** | **98 条全部"编译失败"**，看起来像"模型写得一塌糊涂" |
| 工具的自检用了被测文档的词汇表，而自检样例是另一份文档的 | 自检 4/6 失败，**工具被误报为不可靠**，结果会被整个作废 |
| 输出清单从函数签名里推 | 签名不区分输入和输出，**把输入参数也当成"没定义的输出"**（`psci_func_id` 是输入，被误判）|

**第一个是怎么发现的**：因为**人类专家写的标准答案也 98 条全挂**。标准答案是对的，它挂了就只能是工具坏了——这就是为什么每次都要把标准答案一起跑。

还有一个：直接从 PDF 提取表格（`pdftotext`）会**把某些表格打散成竖排**，导致漏掉输出（`action` 就被漏了），98 条里有 22 条一个输出都提不出来。所以最终改用项目自己抽好的章节文本——**那也正是模型当时看到的那份文本**。

## 怎么复现

```bash
# 找悬空输出
python3 scripts/dangling_alp14.py --gen-dir results/gen98/specs/sel-pr3/alp14

# 找自相矛盾 / 空洞（必须在仓库根目录跑）
python3 scripts/psci_sweep.py --gen-dir results/gen98/specs/sel-pr3/alp14 \
    --preamble training-dataset/specs/alp14/preamble.rs
```

把 `--gen-dir` 换成 `/tmp/goldalp14` 就是跑标准答案的对照。

原始结果在 `results/gen98/dangling/` 和 `results/gen98/sweep/`。
