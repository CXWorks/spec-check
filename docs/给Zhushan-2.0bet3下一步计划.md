## 一、Footprint：2.0 BET3 已经没有这一节了

### 证据

用两种独立的 PDF 提取方式交叉验证过：

```
alp14 :  "Footprint" 小节   98 个（98 条命令，每条一个）
bet3  :  "Footprint" 小节    0 个
```

命令小节的结构变了：

```
alp14:  Interface → Failure conditions → Success conditions → Footprint ✅
bet3 :  Interface → Failure conditions → Success conditions            ← 没有了
```

bet3 全文里 `footprint` 只剩 24 处，**全部在变更日志里**，形如：

> • RMI_RTT_SET_S2AP: add rec.s2ap_addr to footprint (FENIMORE-1113)

以及正文里「memory footprint」这种完全无关的用法。**命令规范里一处都没有。**

### 为什么这就做不了

Footprint 检查的做法是：**把模型生成代码里的状态访问，和文档 Footprint 表里列的状态项做比对**。

alp14 的表长这样：

```
B4.3.45.4 Footprint
  ID          Value
  s2ap_addr   rec.s2ap_addr
```

**2.0 BET3 没有这张表，也就没有比对的基准。**

唯一沾边的是 Context 表多了个 `Before` 列（true/false），但那说的是「读的是命令执行前还是后的状态」，**不等于 footprint 的「这条命令写了什么」**，不能直接顶替。

### 还有一层：这个检查本来也没跑通过

即使在 alp14 上，我们之前也记录过它**不可用**（见 `OUR_CODE_RULE_CHECK.md`）：

> 59 / 98 commands got flagged — clearly mostly false positives, not real bugs.

根因是代码风格不匹配。我们生成的规范把状态显式穿进每个调用：

```rust
RttWalk(new_s, RealmAt(new_s, rd), ...)
```

而文档用的是绑定局部变量：

```
RttWalk(realm, ...)      其中 realm: RealmAt(rd) 在别处定义一次
```

**两种写法做朴素字符串比对必然大面积错配。** 要修得先做表达式归一化（把我们的写法还原成文档的绑定变量形式），那是独立的工程。

**所以 Footprint 这项是两个问题叠加：基准没了 + 工具本来就没通。**

## 二、Z3 逻辑矛盾：能做，但要先补词汇表

### 为什么上次没跑

上次在 bet3 上跑 9B 时，我特意**没有**报编译率和 Z3 结果，原因记在 `specs/bet3/README.md`：

```
编译率    alp14 约 70%   →   bet3 只有 8%（10/121、11/121）
失败主因  missing_symbol（找不到符号）
根因      bet3 用到 186 种类型，旧词汇表里缺 71 种
          RmiResult 出现 104 次 —— 它是 alp14 里 RmiCommandReturnCode 的新名字
```

**Z3 要先把规范编译出来才能判矛盾。编译不过，检查压根没执行。**

这就是我们在 verus_rmm 上反复强调的 `inconclusive`——**不是 0 分，是没考**。

用现在这个词汇表跑，会得到 110/121 编译失败。**那个数字量的是词汇漂移，不是模型能力，报出去会误导。**

### 要做就得给 2.0 BET3 写一份自己的词汇表

好消息是文档里材料是齐的：

| | alp14 | 2.0 BET3 | |
|---|---|---|---|
| 类型定义小节 | 90 | **135** | +50% |
| 函数定义小节 | 206 | **317** | +54% |
| 现成的词汇表 | 88 个 enum/struct + 172 个 spec fn | —— | 需要新建 |

**工作量约是 alp14 那份的 1.5 倍。**

**主要风险**：我在仓库里**没找到生成 alp14 词汇表的脚本**，它可能是 SCOPE 产出或人工整理的。**所以这活可能没有现成工具可复用。**

## 三、计划

### Phase A —— Footprint 做成「发现」（半天，不需要 GPU）

既然查不了，就**把「它被删掉了」这件事本身做扎实**：

1. 系统比对 alp14 和 bet3 的命令小节结构，确认 Footprint 是**整体移除**而不是个别缺失
2. 翻变更日志，看 ARM 有没有说明为什么移除
3. 评估 Context 表的 `Before` 列能否部分替代，给出明确结论
4. 写进文档

**产出**：「2.0 BET3 移除了 Footprint 规范，这类检查在新版上失去基准」——**这是对规范演进的一个观察，本身有价值**，而且解释了为什么这项做不了。

### Phase B —— 建 2.0 BET3 的词汇表（2–3 天，主要工程量）

1. 从 135 个类型小节抽出 enum / struct
2. 从 317 个函数小节抽出签名，生成无函数体的 `pub open spec fn ... ;` 声明
3. **先拿 alp14 验证抽取器**：用同一套流程重建 alp14 的词汇表，和现有那份逐项比对，**对得上才敢用到 bet3**
4. 词汇表自身要能通过 Verus 编译

第 3 步不能省。**上次抽 bet3 章节时就栽过**：`PSCI_VERSION` 因为是章节最后一条命令，一路跑进了后面的 types 小节，抽出来 3554 行（正常是 32 行）。**先在已知答案上验证，是唯一能提前发现这类错的办法。**

**验收标准：bet3 编译率回到 50% 以上。** 达不到说明抽取不完整，不进 Phase C。

### Phase C —— Z3 矛盾检查（半天）

1. 用新词汇表重跑 `psci_sweep.py`，**探测器自检必须 6/6 通过**才认结果
2. **已有的 242 份生成规范可以直接复用，不用重跑模型**（省一次生成）
3. 报 unsat（自相矛盾）/ vacuous（空洞）/ consistent
4. **要写清楚的限制**：bet3 没有人工标准答案，**缺了 gold 这一路对照**。alp14 上我们能说「gold 也是 0 unsat，所以是干净的阴性」，bet3 上说不了这句

### 顺序

**A 先做**（半天出结果，且独立于 B、C）。**B 是长活，C 依赖 B。**

## 四、两件想请你拍板的事

### 1. Footprint 这项怎么处理？

我的倾向是**照实说「2.0 删了这一节，做不了」，同时把这个删除记成一个发现**，而不是硬凑一个替代指标。

硬凑的话只能用 Context 的 `Before` 列，但它测的是另一件事，**做出来的数字没有意义**。

### 2. 值不值得投 2–3 天建 bet3 词汇表？

**我的判断是：优先级低于其他事。** 理由：

- **目前所有真实发现都来自悬空输出检查，而它不需要编译**，不受词汇表影响
- **alp14 上 Z3 跑出来的 unsat 是 0**（连人类专家写的标准答案也是 0）。那是个干净的阴性结论
- **bet3 大概率也是 0**——花 2–3 天很可能得到同样的阴性

**如果目标是多找 bug，我建议先把还没定论的悬空输出确认掉**，比如 `RMI_RTT_DEV_UNMAP` 的 `out_count`（两个配置判断相反，还没结论）。

**如果目标是让这套流程在任意新版本上都能完整跑通**，那 Phase B 该做——而且抽取器做好了，**以后每出一个新版本都能复用**，这是一次性投入。

两个目标都合理，取决于论文要讲哪条线。**你定，我照做。**
