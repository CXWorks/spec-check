# 训练好的 9B：pass rate 多少，能找到几个 bug

## ⭐ 98 条全量重跑（2026-09-12，本节最新）

把 `alp14` 的 **全部 98 条命令**重跑了一遍，五个配置，`research-secure-05` 上 5 张 H100 并行，权重仍是 `sft3-2`（一个字节没改）。

**一句话：98 条千万不能合成一个数报——那样会把正确率虚高 1.5–1.9 倍，而且会让四个不同的配置看起来一模一样。**

### 为什么必须拆成两栏

```
98 条 alp14  =  49 条留出（模型没见过）  +  49 条训练命令（模型见过 alp14 原文和标准答案）
```

那 49 条训练命令，`train.jsonl` 里 `version=alp14` 的样本和它们一一对应，标准答案逐字节相同。**在它们上面的成绩是记忆化上限，不是 eval。**

### 三个值得单独写下的发现

#### 1. 合并报 98 条会虚高 1.5–1.9 倍，而且抹掉配置差异

| 配置 | 池化 98 正确 | 留出 49 正确 | 虚高 |

| 按需选取 | 52/98 (53.1%) | 17/49 (34.7%) | 1.53× |
| 尾部 + 改三轮 | 52/98 (53.1%) | 14/49 (28.6%) | **1.86×** |
| 按需 + 改三轮 | 52/98 (53.1%) | 17/49 (34.7%) | 1.53× |

**注意中间那一列：四个给了字典的配置，池化后全都是 52/98，完全看不出区别。** 而留出集上它们是 14 和 17 —— 差 3 条。**池化不只是数字变好看，是把要测的那个变量直接测没了。**

#### 2. `weaker` 只在没见过的命令上出现

```
训练见过的 49 条：五个配置全部 weaker = 0
留出的   49 条：0 / 1 / 2 / 3 / 2
```

**最危险的那类错——规范放行了标准答案禁止的行为——在训练分布内一次都没发生，全部出现在分布外。** 这和 PSCI 上的空洞爆发是同一个方向：域内安全，域外才暴露。任何只在见过的数据上报 `weaker=0` 的说法都是没有意义的。

#### 3. 一个之前没测过的配置成了新的最好

**`按需字典 + 改三轮`：编译 39/49、正确 17/49、weaker 2。**

在此之前，最好编译是 37/49（尾部+改三轮），最好正确是 16–17/49（按需选取），**两者不可兼得**。这个组合第一次把两项同时拿到，而且 `weaker` 比 37/49 那个配置还低（2 对 3）。

之所以之前没测，是因为历史上那个「字典+改三轮」用的是 tail 还是 selected **没有任何记录**——翻遍 commits、docs、k8s 脚本都没写。这次两个都跑了，结果是 selected 那一支更好。

**但别过度解读**：17 对 14 是 3 条命令，和之前一样不显著。真正硬的结论是第 1 条和第 2 条。

### 这次重跑同时复现了历史数字

同一套流程独立重跑，和文档里记的对照（括号内为原记录）：

| 配置 | 能编译 | 正确 | weaker |
|---|---|---|---|

**`weaker` 四项精确吻合**，编译和正确全部在 ±2 以内。上一节报的那些数字是站得住的。

### 口径与限制

- **正确** = Z3 双向证明与标准答案等价，**且剔除标准答案自己就是空洞（`true`）的命令**（留出 1 条、训练 2 条）。
- **`signature_mismatch` 没有算进任何一栏**：留出集上 `按需+改三轮` 有 6 条、`按需选取` 4 条。这些是生成的函数签名和标准答案对不上，**判不了对错**，所以那两个配置的「正确」栏其实是被低估的。
- 环境：`torch 2.9.1+cu128 / transformers 5.15.0 / peft 0.20.0`（与 k8s 训练/评测的 pin 一致），Verus `0.2026.04.12.f1166c4`，贪心解码 `do_sample=False`。
- **所有差距仍然不显著**，98 条没有改变这一点——它改变的是「哪个数字可以报」。

---
只讲这两个问题。模型是 `sft3-2`（Qwen3.5-9B + LoRA，`dataset_bench` 训练，权重此后一个字节没改过）。

**两句话结论：**

- **pass rate 要看两个数，不是一个。** 最好的配置下**能编译 37/49（75.5%）**，但**真正写对只有 15–16/49（约 31%）**。差了一倍多，报单个数字一定会误导。
  *（上面的 98 条重跑把最好成绩推到编译 39/49、正确 17/49，配置是「按需字典+改三轮」；本节以下保留的是那次重跑之前的记录，两者在 ±2 以内一致。）*
- **能找到 7 个已知真 bug 里的 6 个**（eac5 3/4 + rel0 3/3），外加另一张纯文字考卷满分 16/16。**这两个数字都已在本地用 Verus 重跑复算通过**（详见第三节）。

## 一、pass rate

### 先分清楚「pass」指什么

评测脚本里的 `pass` = **这份规范能通过 Verus 编译**。它**不代表写对了**。判断写对了是另一套流程：让 Z3 去证明模型写的式子和标准答案**语义等价**。

所以下面每张表都有两列，请优先看「正确」那一列。

### 留出集 49 条（模型训练时一次都没见过，统一在 `alp14` 文本上考）

| 考试时给它什么 | 能编译 | **正确** | weaker（危险错） |
|---|---|---|---|
| 什么都不给 | 22/49 (44.9%) | **11/49 (22.4%)** | **0** |
| 字典 = 尾部 200 行 | 27/49 (55.1%) | 15/49 (30.6%) | 1 |
| 字典 = 按需选取 | 29/49 (59.2%) | **16/49 (32.7%)** | 2 |
| 字典 + 编译报错后改三轮 | **37/49 (75.5%)** | 15/49 (30.6%) | 3 |

`正确` 的精确定义：Z3 双向证明与标准答案等价，**并且剔除掉标准答案自己就是空洞（`true`）的那些命令**——跟一个空的东西「等价」是白送的。这一条剔除在 49 条里只影响 1 条（`PSCI_CPU_OFF`），但在 `rel0` 那批上影响 6 条，不剔会虚高。

### 这张表里最该注意的三件事

**1. 编译率涨了 15 条，正确率只涨了 4 条。**

从 22→37 多出来的 15 条能编译的规范里，只有 4 条是对的。**编译修复循环修的是语法，不是内容。**

**2. weaker 从 0 涨到 3，方向和编译率完全相反。**

`weaker` = 模型写的规范**放行了标准答案禁止的行为**，是最危险的一类错（极端情形就是写一句 `true`：编译百分百通过，允许一切）。

**如果论文里要写「9B 零 weaker」，支撑它的配置是「什么都不给」那一行，不是成绩最好那一行。** 这两个 claim 不能同时用。

**3. 域内的 pass 不是靠写空话刷出来的——这点我专门查了。**

22 条通过的规范里，**只有 1 条函数体是 `true`**（`PSCI_CPU_OFF`，而标准答案在这条上也是 `true`，所以它是对的）。

这一点值得和 PSCI 那份文档上的表现对照着看：同一个 9B 在 PSCI 上 16/22 的函数体字面就是 `true`（73%）。**空洞是出域才爆发的问题，域内没有。**

### 编译不过的 27 条，卡在哪

| 失败原因 | 条数 |
|---|---|
| `wrong_arity`（函数调用参数个数不对） | 9 |
| `missing_symbol`（用了字典里没有的名字） | 6 |
| `type_mismatch` | 5 |
| `unbalanced_delimiter`（括号没配平） | 3 |
| `bad_field_access` | 2 |
| 其他 | 2 |

**`wrong_arity` 是最大的单一失败原因**，而且它正好卡在找 bug 最关键的那几条命令上（见下面第二节）。这不是「模型不懂语义」，是「模型没看见自己写的那一行」——修复提示里给了声明和行号，**但没给它自己写错的那个调用**。

### 一个必须写下的天花板

评测 JSON 自己记着：**`gold compiles on 33/40 (82.5%) with this Verus build`**。

标准答案在这个 Verus 版本上都有 17.5% 编译不过。**模型的编译率不是在跟 100% 比。**

## 二、能找到多少 bug

### 两张考卷

| 考卷 | 考什么 | 满分 | 要不要 Verus |
|---|---|---|---|
| `rule_check_8bugs` | 纯文字检查：文档声明了一个输出却从没定义它，模型有没有把它留空。**留空 = 发现了漏洞** | 16 项（eac5 8 + rel0 8） | 不要 |
| `verus_rmm` | 真编译，让证明器判定矛盾。难得多 | **eac5 4 项 + rel0 3 项 = 7 个真 bug** | 要 |

### 考卷 1：rule_check —— 满分

| | recall | 误报 |
|---|---|---|
| **9B** | **16/16** | 2 |
| 4B | 11/16（eac5 6/8，rel0 5/8） | 0 |
| 标准答案 | 16/16 | 0 |

**9B 在这张卷上和标准答案打平。** 4B 漏掉的是 `RMI_VERSION`、`RSI_VERSION`、`RSI_IPA_STATE_GET`。

那 2 个误报是**同一条命令在两个版本上的同一处**：`RMI_RTT_READ_ENTRY.desc`。有点意思的是，`RMI_RTT_READ_ENTRY` 正是那条「文档声明了 `walk_level` 却从没定义它」的命令——模型在这条上多留空了一个字段。

### 考卷 2：verus_rmm —— 7 个真 bug 里最好找到 6 个

| 配置 | eac5 TP | rel0 TP | 合计 |
|---|---|---|---|
| 9B 什么都不给 | 1/4 | 1/3 | **2/7** |
| 9B + 一轮修复（只跑了 eac5） | 1/4 | — | — |
| **9B + 字典 + 改三轮** | **3/4** | **3/3** | **6/7** |
| 4B 什么都不给 | 0/4 | 1/3 | 1/7 |
| 4B + 字典 + 改三轮 | 2/4 | 2/3 | 4/7 |
| 标准答案 | 4/4 | 3/3 | 7/7 |

**`rel0` 上 3/3，逐项与标准答案相同。**

### 这张表最容易读错的地方：没找到 ≠ 判断错了

verus_rmm 有第三种结果叫 **`inconclusive`（无结论）**：模型写的东西编译不过，**检查根本没跑起来**。这不是 0 分，是「没考」。

我今天重跑基线，逐项日志是这样的：

```
9B 什么都不给，eac5 的 10 个检查项：
  TP  RMI_DATA_DESTROY:ripas                  inconclusive  （参数个数不对）
  TP  RMI_RTT_DESTROY:state                   inconclusive  （找不到 RMI_SUCCESS）
  TP  RMI_RTT_INIT_RIPAS:ripas                inconclusive  （找不到 walk_top）
  TP  RSI_ATTESTATION_TOKEN_CONTINUE          detected      ← 唯一真正跑起来的
  FP  ×6                                      全部 inconclusive
```

**4 个真 bug 里，3 个是「没跑起来」，不是「判错了」。**

这也解释了 FP 那一列：基线的 `0/6 误报`**不是「它很谨慎」，是 6 个检查全都没跑起来**。编译率上去之后 FP 才开始触发，而 FP 触发**是对的**——那 6 道题是出题工具 SCOPE 自己错了，标准答案也全触发（6/6）。所以这一列的判断标准是**离 gold 的 6/6 有多近**，不是越低越好。

**结论：找 bug 的瓶颈是编译，不是理解。** 这和第一节 `wrong_arity` 排第一是同一件事。

### 那 3/4 和 3/3

一度复算不了，因为产物不在仓库里而在 HF 上，而当时的 token 已失效（401）。换上有效 token 后取回 `gen/sft3-2-final-prerep3.tgz` 和 `gen/sft3-2-final-pr3all.tgz`，本地 Verus 重跑：

```
sft3-2-final-prerep3  eac5    TP 3/4   FP 5/6   inconclusive 1
sft3-2-final-pr3all   eac5    TP 3/4   FP 5/6   inconclusive 1
sft3-2-final-pr3all   rel0    TP 3/3   FP 6/6   inconclusive 0   ← 与标准答案逐项相同
```

**`rel0` 上 3/3 + 6/6 + 零 inconclusive，和 gold 一模一样**——不只是 TP 追平，连 6 个 FP 项的触发情况和「每一项都真的跑起来了」都一致。

顺带澄清一个曾经的疑点：仓库里的 `results/benchmark_gen/sft3-2-repaired` **不是**产生 3/4 的那份产物，它是 8 月 18 日那次**只改一轮、且没给字典**的实验，提交信息自己写着 `0/4 → 1/4`，我重跑得到 1/4，**对得上，不矛盾**。

### 留下来的两条运维教训

1. **产物不该只存在一个会过期的 token 后面。** 这次被绊住两次。建议把 `prerep3` / `pr3all` 提交进仓库（几十个 `.rs`，几百 KB），或落到 PVC 上。
2. **Verus 本地缺失已解决**——Verus 0.2026.04.12 + rustup 1.94.0 装在会话临时目录，**没动 home、没改 PATH**，删目录即卸载。要长期本地跑值得正式装一次。

## 四、三个必须同时写下的限制

1. **真 bug 的分母只有 7。** 6/7 和 5/7 差一个样本。这个数字撑不起强 claim。
2. **成绩最好的配置，恰好是 weaker 最差的配置**（0 → 3）。「找到最多 bug」和「不写危险规范」在现在的数据里是冲突的，得挑一个来讲。
3. **表里没有任何一个差距是统计显著的**（9B 按需选取 vs 什么都不给：编译 +7 p=0.065、正确 +5 p=0.180）。

## 五、下一步（就这两个问题而言）

1. **修那个 `wrong_arity`。** 它是编译失败的第一大原因（9/27），而且正好卡在 verus_rmm 的真 bug 项上。修法是现成的、由九次失败指出来的：**修复提示里把模型自己写错的那一行贴给它**，而不是只给声明和行号。现在的提示对 `missing_symbol` 管用（那是个替换题），对 `wrong_arity` 没用（模型看不见自己的调用点）。这一步直接关系到能不能从 6/7 摸到 7/7。
