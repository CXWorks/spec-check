# 六份规范上跑 rule-based check：计划

> **目标**：在 `specs/` 的 6 份规范文档上，用**微调 9B** 和**原始 9B** 各跑一遍，做 rule-based 检查（查悬空输出），看能找到多少文档缺陷。
>
> **算力**：`jisenli-dev-0`（node 090，8×H100 全空）。

---

## 一、先说三件会改变计划形状的事

### 1. rule check 不需要能编译的词汇表 —— 但有半个例外

preamble 在这套流程里有**两个完全不同的用途**，不能混为一谈：

| 用途 | rule check 需要吗 |
|---|---|
| 给模型看的**提示词上下文**（「尾部 200 行」「按需选取」按这个分）| 需要一份**文本**，但**不必能编译** |
| **Verus 编译上下文**（「改三轮」靠编译报错驱动）| **完全不需要** |

所以 5 个配置里：

```
不给字典        ✅ 直接能跑
尾部 200 行      ✅ 只要有词汇表文本，不必合法
按需选取        ✅ 同上
尾部 + 改三轮    ❌ 修复循环本身就是 Verus 驱动的
按需 + 改三轮    ❌ 同上
```

**那两个「改三轮」不是被词汇表卡住，是这个配置的定义就依赖编译。**

### 2. 而且有数据表明：改三轮不改变 rule check 结果

alp14 上跑过全部 5 个配置的悬空输出检查，**修复配置和对应的非修复配置结果一致**：

```
RMI_PSMMU_IRQ_NOTIFY    nopre / sel / sel-pr3 / tail / tail-pr3   全部留空
RMI_RTT_READ_ENTRY.desc              tail 和 tail-pr3 都留空
```

原因很直接：**「输出没被约束」不是编译错误**，修复循环看不见它，也就改不动它。

**结论：对 rule check 而言，有意义的是 3 个配置，不是 5 个。** 为跑那 2 个修复配置去建可编译的词汇表，是在为一个已知不会变的结果付钱。

### 3. 6 份文档里只有 1 份是就绪的

| 文档 | 页数 | 章节抽取 | 词汇表文本 |
|---|---|---|---|
| **PSCI** DEN0022F.b | 96 | ✅ 22 条 | ✅ 126 行 |
| SDEI DEN0054C | 65 | ❌ | ❌ |
| SCMI DEN0056F | 224 | ❌ | ❌ |
| FFA DEN0077A | 360 | ❌ | ❌ |
| DRTM DEN0113 | 100 | ❌ | ❌ |
| RISC-V SBI | 111 | ❌ | ❌ |

而且**每份的结构都不一样**，通用正则无效：

```
SDEI    5.1.2  SDEI_EVENT_REGISTER      编号 + 大写名
FFA     13.2   FFA_VERSION              同上
DRTM    3.2    DRTM_VERSION             同上，多一层 3.2.1 usage 子节
SCMI    按协议组织，命令名无统一前缀        ← 结构最不同
SBI     sbi_xxx()  小写函数式             ← 结构最不同
```

**5 份各要一套抽取器。这是真正的工作量。**

## 二、rule check 要什么

两样东西，**都不需要 Verus**：

1. **逐条命令的章节文本** —— 喂给模型
2. **每条命令声明了哪些输出** —— 用来判断有没有悬空

第 2 项各文档格式差别很大：

| 文档 | 返回值的写法 | 难度 |
|---|---|---|
| PSCI | 已处理 | ✅ |
| **SCMI** | **结构化 `Return values` 表（145 处）** | 最好做 |
| **SDEI** | `Return` 块 + `Parameters` 表（18 处） | 好做 |
| DRTM / FFA / SBI | 有 `Returns` 段落，**没有结构化表格** | **难，要解析散文** |

---

## 三、六份都没有标准答案

**「正确 / weaker」测不了**（那要和 gold 做 Z3 等价判定）。

能测的只有：**悬空输出**（rule check 的主体）、`vacuous` 空洞、能编译。

## 四、计划

### Phase 0 — 原始 9B 跑通（半小时）

`gen_specs.py` 的 `--adapter` 本来就是可选参数，**省掉就是原始模型，代码不用改**。在 PSCI 上跑 2 条冒烟确认。

> 这个 base vs 微调的对照一直没做过。**它回答一个硬问题**：微调在域外究竟是「没帮上忙」还是「损害了泛化」——这两个结论对论文含义完全不同。

### Phase 1 — PSCI 全矩阵（半天，立刻可做）

```
22 条 × 2 模型 × 3 配置 = 132 次生成    8 卡并行约 20 分钟
```

PSCI 是唯一现成的。出第一组 base vs 微调对照，并验证整条链路。

### Phase 2 — 5 份文档的抽取器（4–5 天，**主要工作量**）

按难度排序，先易后难：

| 顺序 | 文档 | 难点 | 估时 |
|---|---|---|---|
| 1 | **SCMI** | 输出表最规整，反而最好做 | 0.5 天 |
| 2 | **SDEI** | 65 页最小 | 0.5 天 |
| 3 | DRTM | 返回值是散文 | 1 天 |
| 4 | SBI | 小写函数式，结构不同 | 1 天 |
| 5 | FFA | 360 页最大 + 散文返回值 | 1–1.5 天 |

**每份都必须「拿已知答案验证」**：用同一套流程重跑 PSCI，和现有 22 条逐条比对，**对得上才敢用到新文档**。

上次抽 bet3 时 `PSCI_VERSION` 抽出 3554 行（正常 32 行），就是因为它是章节最后一条、一路跑进了后面的 types 小节——**漏了这一步验证**。

### Phase 3 — 全量生成 + rule check（1–2 小时）

```
约 250 条 × 2 模型 × 3 配置 = 1500 次生成   8 卡并行约 1.5 小时
```

「尾部 / 按需选取」两个配置需要每份文档一份**词汇表文本**——从文档自己的类型/常量小节粗抽即可，**不必合法可编译**，5 份约半天。

---

## 五、GPU 不是瓶颈

```
全部生成（Phase 1 + 3）：  8 卡并行约 2 小时
抽取器工程：              4–5 天
```

**8 张卡远远够用。成本全在文档工程，不在算力。**

---

## 六、执行顺序与理由

**先做 Phase 0 + 1**，半天出 base vs 微调在 PSCI 上的对照。

**这一步投入最小、信息量最大**：如果原始模型在域外和微调版差不多甚至更好，会直接影响后面铺 5 份文档还值不值得——也直接影响论文主线该放「流水线」还是「微调模型」。

**Phase 2 先做 SCMI + SDEI**（各半天）。这两份做完就能验证「一套流程能不能跨文档复用」——**那正是论文要卖的点**。DRTM / FFA / SBI 的散文式返回值是真难点，放后面。

## 附：会一起记录的限制

- **6 份都没有 gold**，所以正确率测不了，只报悬空输出和空洞
- **rule check 只筛候选，不产出结论**。候选要对着原文人工确认才算 bug——alp14 那次 11 条候选里最后只有 2 条是真文档缺陷，9 条是模型自己漏读
- **PSCI 上已知的历史结果**：微调 9B 在 22 条里有 16 条写出空洞规范（函数体字面就是 `true`），这次会和原始模型对照着看
